## Decisions

**P11-T4 · undo mechanism.** The plan's `setRangeText`-lands-on-the-undo-stack assumption is
false in Chromium (Ctrl+Z restored nothing — proven by a failing Playwright test before the
fix). I switched programmatic writes to `document.execCommand('insertText')`, which is
deprecated but is *the* undo-participating API in Chromium/Electron and the only runtime our
webviews have; `setRangeText` stays as a functional fallback. Recorded as a phase deviation.

**P11-T4 · protocol split for the message.** Programmatic writes (history pick, amend
prefill, post-commit clear) now ride a dedicated `commit/message` event, and the editor
ignores `CommitStateDto.message` after init. Reason: a generic state push can carry a
snapshot older than the 250 ms-debounced persist, and adopting it mid-typing would eat
keystrokes. Known micro-tradeoff: reloading the whole window within 250 ms of the last
keystroke can lose that tail (host wins at init) — versioning the message to close that
sliver wasn't worth the machinery.

**P11-T4 · dropdowns.** History clock + new `Amend last commit ▾` render as in-webview kit
menus fed by two new data RPCs; `commit/showHistory` is gone. The native
`gittree.commit.showMessageHistory` QuickPick still works in both surface modes.

**P11-T5 · deferred checks default ON — a behaviour change you should know about.** The §2A
reference shows `[x] Run advanced checks after a commit is done` checked with "Failed checks
will not prevent a commit" — IntelliJ's shipped default. I made
`gittree.commit.checks.deferAdvanced` default **true**, so Analyze/TODO now report after the
commit instead of gating it. The old gating mode is fully kept behind the toggle (phase03's
gate test pins it off explicitly). If you'd rather keep gating as the default, it's a
one-line default flip + phase doc edit.

**P11-T5 · deferred pass re-baselines on the commit's parent.** Post-commit, worktree↔HEAD is
empty — the TODO check would have found nothing, silently. `CheckContext.baseRev` now carries
`<new-commit>^` for the deferred pass. Caught by reasoning before the test caught it; the
integration test proves the finding arrives with `headSha == new HEAD`.

**P11-T5 · Rearrange code omitted entirely** (plan allowed language-conditional): there is no
cross-language rearrange code-action kind, and probing would execute every provider. Cleanup's
"Choose profile" maps to the fix-all kind (`cleanupKind`, e.g. `source.fixAll.eslint`).

**P11-T5 · author is workspaceState, not a setting.** The plan self-contradicts (contributions
list says setting, step 2 says per-repo workspaceState); a setting cannot be per-repo in
multi-root, so step 2 wins.

**P11-T6 · "already unshelved" needed new store state.** IntelliJ greys applied-but-kept
entries; P7's store had no such concept (entries were deleted or untouched). I added an
optional `unshelvedAt` marker to `ShelfMeta` (absent on old entries = not unshelved, so
existing stores are untouched), set on a clean full unshelve that keeps the entry. The
`Show already unshelved` toggle is a workspace setting consumed by both the tab and the
tree so the two can't disagree.

**P11-T6 · tab actions = tree commands.** Every Shelf-tab action (toolbar AND native
context menu) dispatches the registered `gittree.shelf.*` command with `{repoRoot, shelfId}`.
The "same state from both surfaces" acceptance is true by construction, and the integration
test proves it end-to-end. Context menus are VS Code-native since all labels are static.

**P11-T6 · error banner promoted to window level.** It lived inside the Commit TabPanel, so
a failed shelf action was invisible from the Shelf tab. Caught by a new Playwright test.

**P11-T7 · two plan mechanisms replaced.** (1) The partial-shelve patch is produced by git
from a scratch index (the T3 technique), not by `buildPatch` — buildPatch emits zero-context
hunks the unshelve `--index`/`--3way` ladder can't consume. (2) Removal writes the computed
residue (`applyLineChanges` of the complement) instead of reverse-applying a complement patch,
which fails on adjacent hunks. Both in the phase doc's deviations.

**P11-T7 · `git apply --3way` implies `--index`.** Found by the round-trip integration test:
unshelving onto a residue failed with "does not match index" because I had reset the index to
HEAD. The residue is now left staged (index == worktree) so the 3way blob-merge path opens.
Consequence you may notice: after a partial shelve the remaining changes show as *staged* in
the staging paradigm; changelists (our default) reads both alike, and unshelve unstages after.

**P12-T8 · redaction sits at the ring's front door, not the renderer.** `CommandLog.push`
redacts argv and output (URL userinfo, askpass values, `token/password/secret=`, `--author=`)
*before* anything enters the buffer, so no secret can exist in the ring, cross RPC, or reach
the DOM — the webview renders what it gets. Unit tests pin the tokenized-URL and askpass
cases from the acceptance line. The ring holds 2 000 entries (output head capped at 2 000
chars per entry), so memory is bounded by construction.

**P12-T8 · test lesson: a saturated ring makes size assertions meaningless.** The first cut
of the integration test asserted `size >= before + 2` after two runs — but by the time the
P12 suite executes in a full run, thousands of gits have already filled the ring to its cap,
so size can never grow. The seq cursor (`entriesAfter(lastSeq)`) is the only honest witness
that specific runs arrived; the clear assertion likewise tolerates background refresher
pushes racing the check (everything pre-clear gone, not "git went quiet").

**P12-T8 · `gittree.log.console.limit` is read once at activation.** Live-resizing a ring
buffer has churn and no user story; the setting exists for constrained hosts. Values < 100 or
non-finite fall back to 2 000.

**P12-T8 · failed rows are pre-expanded but still collapsible.** First cut used
`open = failed || toggled` — a failed row's chevron was a silent no-op. Switched to XOR
(`open = failed !== toggled`): failures default open, successes default closed, the chevron
always works. Playwright pins both directions.

**P12-T8 · the Log pane's sizing had to move to `useElementSize`.** `TabPanel` unmounts the
inactive tab, so switching Log → Console → Log remounts the commits pane; the old

never see another resize (the exact P11-T4 lesson, resurfacing). The callback-ref hook
re-attaches per element. Also: the Console tab refetches the full (capped) ring on
`log/consoleChanged` instead of a delta — a host-side clear resets seqs below the webview's
cursor, and the full read is cheap at ≤2 000 entries.

**P13-T1 · `--set-upstream` only when publishing under the branch's own name.** A push

**P13-T1 · what "outgoing" means when the target branch does not exist yet.** With a tracking
ref we use `<tracking>..HEAD`. Without one, we use `HEAD --not --remotes=<remote>` — i.e. what

Consequence worth knowing: pushing an already-published branch to a *new* remote name reports
only the commits made since the last push, not the whole branch. That surprised my own first
test assertion; it is the correct model (it is exactly what IntelliJ shows for a new branch cut
from `main`), so I fixed the test, not the code. The diff base falls back to the span's
boundary parent and then to the empty tree for a root-spanning push — the P12-T3 rule.

**P13-T8 · the finding that shaped the task: git has already applied the non-conflicting
changes.** IntelliJ's merge viewer models *every* base↔side difference as a "change", so its
`Apply non-conflicting changes: Left / All / Right` has plenty to do. Geet's blocks come from
`git merge-file -p --diff3` over the index stages — and I verified empirically that a change one
side makes with no counterpart on the other **never appears inside a conflict block**: git
applies it and conflicts only on overlapping regions. So Left/Right act on what remains *inside*
the blocks, and when nothing there is one-sided they report `No non-conflicting changes to apply`
with the live counter instead of quietly taking a side. `All` still runs the wand's full cascade,
including the two-sided rules (interleave, whitespace-only) a one-sided apply must never use.
Recorded as deviation **D17**. **My first fixture was wrong for exactly this reason** — it
assumed one-sided blocks would exist; the replacement builds two blocks of deliberately
different kinds (one interleave-resolvable, one genuine conflict) and asserts that Left and Right
*decline* the two-sided one while All takes it. That is the safety property worth pinning.

**Test harness · `refServices` is keyed by canonical root, not insertion order.** My first cut

**P13-T6 · your git is 2.28, and that changes what worktree management can read.** `locked`
and `prunable` only reached `git worktree list --porcelain` in **2.36**. On 2.28 the porcelain
says nothing about either, so a straight implementation would ship a Worktrees view that can
never show a lock badge and a Prune that never marks anything stale — working code that does
nothing visible on your machine. `augmentFromDisk` derives both from git's own layout instead
(a linked worktree's `.git` is a pointer file to its admin dir; a lock is a `locked` file there
whose contents are the reason; a missing directory is prunable by definition). It only ever
*adds*, so a newer git keeps what it reported. Recorded as deviation **D16** and deletable once
2.36 is the floor. **If you upgrade git, nothing breaks — the two agree.**

**Test harness · `os.tmpdir()` is an 8.3 short path and git prints the long one.** Every
worktree path comparison failed until the suite canonicalized its temp root once with
`realpathSync.native`. The same 8.3 gotcha `canonicalKey()` exists for, in a new place.

**Test harness · a 30 s suite teardown was not enough and failed a whole run.** P13's teardown
does two *retrying* git config writes — `gitWithRetry` can spend ~22 s each under the Windows
lock contention it exists for — plus a recursive delete of a tree holding a bare repo, a clone
and worktrees. Raised to 180 s with retrying `rmSync`. A teardown that does real work needs a
timeout sized for its worst case, not its typical one.

**Test harness · the P12 symref flake cascade fired again.** Same root cause as before
(`git checkout feature/f2` → "unable to write symref for HEAD: Permission denied"), taking four
follow-on P12 tests with it, and again it did not recur on the next run. Two sightings now in
one night; see the blocker list.

**Test harness · `refreshNow()` is not a barrier, and that cost me two false failures.** Two
P13 tests passed in isolation and failed in the full run: `refreshNow()` can resolve against a
refresh that *started before* the write under test, so reading `model.snapshot` immediately
afterwards is a race that only shows up under contention. Added a `waitForStatus()` helper to
the suite that waits for the fact (the path appearing, the stash existing) instead of trusting
the refresh, and used it everywhere the suite reads the snapshot after a write. **Any test that
writes then reads the model needs a wait, not a refresh.**

**Test harness · `delete process.env['GITTREE_TEST_AUTOCONFIRM']` was a live landmine.** The
runner sets it once for the whole process, and `phase07`/`phase09` deleted it in their
`finally` blocks — silently disarming auto-confirm for every suite that ran afterwards. Nothing
depended on it until P13-T2's reset test, which then failed in the full run with VS Code's
"DialogService: refused to show dialog in tests" while passing in isolation. Fixed at the root:
new `withAutoConfirm()` helper in `test/integration/setup.ts` saves and restores, and all four
old sites plus both P13 sites use it. **Never `delete` a harness-global in a suite.**

**P13-T2 · the "no upstream" test builds its own case.** The first cut borrowed "some other
workspace repo has no upstream" and failed: `phase01` leaves an `origin` on repo A, and
`phase12` leaves branch config behind on repo C. Shared fixtures accumulate configuration
across a run, so a test that needs a *state* must create it (unset the upstream, assert,
restore) rather than assume some repo still has it.

**Test harness · the P5-family symref flake now cascades.** One full run had
`git checkout feature/f2` fail with "unable to write symref for HEAD: Permission denied" inside
**P12**, which left repo C on the wrong branch and took four more P12 tests down with it
(8 failures from one root cause). It did not recur on the next run. Same documented
AV/indexer contention as the P5 sighting; nothing in the product changed. Worth knowing that a
single symref flake can look like a broad P12 regression.

**Test harness · the P7-T2 500 ms stash bound is now borderline on this host, and it is not
P13's doing.** It failed in both full runs (531/529 ms) *and* in isolation, unlike yesterday. I
did not take that at face value: I put `registerPhase13Dialogs` behind a temporary env seam and
measured both ways — **P13 disabled → 3/3 failures (537, 515, 539 ms); P13 enabled → 2/3
failures (522, 527 ms)**. The measurement sits squarely on the bound either way, so the
registration is exonerated and the machine is simply slower than the budget assumes. Seam
removed; budget NOT loosened. Fixtures are `mkdtemp`-fresh per run, so this is not accumulated
fixture state — see the blocker below.
